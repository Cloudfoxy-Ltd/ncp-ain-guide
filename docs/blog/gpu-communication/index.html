1. Why do GPUs need to talk?

Big AI models are trained on many GPUs at once. One GPU alone would take months. So we split the work.

The most common way is called data parallel training. Every GPU holds a full copy of the model. Each GPU learns from a different slice of the data. Then, after every small step, the GPUs must share what they learned so all copies stay the same.

That sharing happens thousands of times. If it is slow, the expensive GPUs sit idle and wait. This is why GPU-to-GPU communication matters so much.

Think of it as

Four students each mark a quarter of the exam papers. At the end they must add up their totals and agree on one class average. The marking is fast. Walking around to share totals is the part we want to make quick.

2. Five words you need

Let's treat data like parcels and the connections like roads. Then the rest of this post is easy.

BandwidthHow wide the road is. How many GB per second can pass.
LatencyHow long the first parcel takes to arrive, even on an empty road.
CopyEach time data is put down and picked up again. Every copy costs time.
HopOne trip from one box to the next. Fewer hops is usually better.
CollectiveA group move where many GPUs take part, like "everyone add up and share".

3. Inside one server: the slow way and the direct way

Inside a server, GPUs plug into PCIe. PCIe is the standard road that connects the CPU, memory, GPUs and network cards.

In the old way, data from GPU 0 goes up to the CPU's memory first, then down to GPU 1. With peer-to-peer (P2P), GPU 0 writes straight into GPU 1's memory. Press the buttons to compare.

P2P removes the extra stop. But the PCIe road is still fairly narrow, and it is shared with everything else in the server. For AI, we need something much wider.

4. NVLink and NVSwitch: the GPU motorway

NVLink is NVIDIA's own direct cable between GPUs. It is many times wider than PCIe.

NVSwitch is a chip that joins all the NVLinks together. In an 8-GPU server (like an HGX H100 or B200 board), every GPU can talk to every other GPU at full speed, at the same time. No GPU has to wait for another.

5. Between servers: TCP, RDMA and GPUDirect RDMA

One server holds 8 GPUs. Big training jobs use hundreds or thousands. So data must also travel between servers, through a network card (NIC) and a network switch.

There are three ways to do this. They differ in how many copies are made and how much the CPU has to help.

  • TCP (normal networking): works everywhere, but the CPU copies data several times.
  • RDMA (Remote Direct Memory Access): the NIC reads and writes memory by itself. No CPU copies. It runs on InfiniBand or on Ethernet as RoCE.
  • GPUDirect RDMA: the NIC reads and writes GPU memory directly. The CPU and system memory are skipped completely.
Think of it as

TCP is sending a parcel through two post offices and two sorting rooms. RDMA is a courier who picks up from your warehouse. GPUDirect RDMA is a courier who walks straight into your workshop and takes the parcel off your desk.

One detail matters a lot: GPUDirect RDMA is fastest when the GPU and the NIC sit on the same PCIe switch. That is why AI servers usually pair one NIC with each GPU.

6. How fast is each road?

Here is a race. Each road moves the same 10 GB of data. The numbers are approximate peak speeds in one direction. Real speeds are a bit lower.

Notice two things. First, NVLink inside a server is around 10 times faster than one network card between servers. Second, this gap is why smart software must choose the right road for each job. That software is NCCL.

7. Meet NCCL

NCCL (say "nickel") is the NVIDIA Collective Communications Library. It is the piece of software that moves data between GPUs for AI training and inference.

You almost never call NCCL yourself. PyTorch, JAX, DeepSpeed, Megatron and others call it for you. When PyTorch says backend="nccl", this is what runs.

NCCL does three jobs:

  1. Finds the roads. At start-up it maps every GPU, NVLink, PCIe switch and NIC in the system.
  2. Picks a plan. It chooses an algorithm (ring, tree or in-switch) and a road for each piece of data.
  3. Moves the data. It runs small GPU programs that copy, add and forward data, very fast, without the CPU.

8. The six team moves (collectives)

A collective is a move that a whole group of GPUs does together. NCCL has a small set of them. Once you know these six, you can read almost any AI training log.

In the diagram, each GPU's data is cut into four pieces. The colour tells you whose data it is. When pieces are added together, they show stripes of every colour inside them.

Here is a useful trick: AllReduce = ReduceScatter + AllGather. First everyone adds up and keeps one share. Then everyone shares their finished share. That is exactly how the ring works, as you will see next.

9. The ring, step by step

The simple AllReduce above sends everything to GPU 0. That makes GPU 0 a traffic jam. NCCL's favourite answer is the ring.

The GPUs stand in a circle. Each one only talks to its right-hand neighbour. Data is cut into as many pieces as there are GPUs. Every GPU sends at the same time, so every link is busy all the time. Use the buttons to walk through it.

The magic: each GPU sends only 2 × (N − 1) / N of its data. With 4 GPUs that is 1.5 times. With 1,000 GPUs it is still just under 2 times. The amount each GPU sends does not grow as you add GPUs. That is why the ring is so popular for big messages.

10. Ring, tree or switch?

The ring has one weak spot: it needs 2 × (N − 1) steps. Each step adds a little delay. With small messages and many GPUs, those delays add up. So NCCL has other plans too.

PlanSteps for 8 GPUsBest forNCCL name
Ring14Big messages. Uses every link fully.Ring
Tree6Small and medium messages across many servers.Tree
In-switch2Systems with NVSwitch (NVLS) or SHARP InfiniBand switches.NVLS, CollNet

You don't have to choose. NCCL measures the system and picks the best plan for each message size by itself.

11. How NCCL picks the road

At start-up, NCCL builds a map of the machine. For every pair of GPUs it asks a few simple questions, then picks the best road. Choose a situation:

Three more ideas that make NCCL fast

Channels (more lanes). NCCL does not run just one ring. It runs several at once, called channels. Each channel takes part of the data, uses some of the GPU's cores, and can use a different NIC. More channels means more lanes on the motorway.

Protocols (how parcels are packed). NCCL has three ways to pack data:

  • LL (Low Latency): tiny packets with a built-in "ready" flag. Very quick to start, but half the space is used by flags. Good for small messages.
  • LL128: bigger 128-byte packets, almost all data. Fast and efficient, mainly over NVLink.
  • Simple: large blocks with a separate "ready" signal. Best bandwidth for big messages.

PXN and rails. In big AI clusters, GPU 0 of every server connects to the same group of switches, GPU 1 to another group, and so on. These groups are called rails. If GPU 3 needs to send to a GPU on a different rail, NCCL can first hop over NVLink to the GPU that sits next to the right NIC, then go out on the network. This trick is called PXN (PCI × NVLink). It keeps traffic on the fast, short paths.

12. Try it yourself

NVIDIA provides a free test kit called nccl-tests. It is the first thing to run on any new GPU server or cluster.

# build the tests
git clone https://github.com/NVIDIA/nccl-tests.git
cd nccl-tests && make

# one server, 8 GPUs: AllReduce from 8 bytes up to 8 GB
./build/all_reduce_perf -b 8 -e 8G -f 2 -g 8

# many servers with MPI (build with: make MPI=1)
mpirun -np 16 -N 8 ./build/all_reduce_perf -b 8 -e 8G -f 2 -g 1

The output has two speed columns. They confuse many people, so here is the simple version:

  • algbw (algorithm bandwidth) = data size ÷ time. Easy, but it changes with the number of GPUs.
  • busbw (bus bandwidth) = algbw × 2(N − 1)/N for AllReduce. This is the number to compare with your hardware's link speed. If busbw is close to the link speed, your system is healthy.

To see which roads NCCL picked, turn on logging:

NCCL_DEBUG=INFO ./build/all_reduce_perf -b 1G -e 1G -g 8

# look for lines like these:
NCCL INFO Channel 00/16 :    0   1   2   3   4   5   6   7
NCCL INFO Channel 00/0 : 0[0] -> 1[1] via P2P/CUMEM
NCCL INFO NET/IB : Using [0]mlx5_0:1/IB [1]mlx5_1:1/IB ...
NCCL INFO Channel 00/0 : 8[0] -> 0[0] [receive] via NET/IB/0/GDRDMA

P2P means direct GPU to GPU (NVLink or PCIe). NET/IB means RDMA over InfiniBand or RoCE. GDRDMA means GPUDirect RDMA is on. If you see NET/Socket on a cluster that has RDMA NICs, something is set up wrong.

13. Cheat sheet

NCCL is controlled with environment variables. These are the ones you will meet first. Change them for testing and troubleshooting. In normal use, NCCL's own choices are usually best.

VariableWhat it does
NCCL_DEBUG=INFOPrints what NCCL found and which roads it chose.
NCCL_DEBUG_SUBSYS=INIT,NETOnly show some parts of the log (start-up, network...).
NCCL_IB_HCA=mlx5_0,mlx5_1Which RDMA network cards NCCL may use.
NCCL_SOCKET_IFNAME=eth0Which normal network port to use for start-up and for TCP.
NCCL_IB_GID_INDEX=3For RoCE: which address entry to use (often RoCE v2).
NCCL_NET_GDR_LEVELHow "far apart" a GPU and NIC can be and still use GPUDirect RDMA.
NCCL_P2P_DISABLE=1Turns off direct GPU-to-GPU. Useful only to test if P2P is the problem.
NCCL_ALGO=RingForces an algorithm (Ring, Tree, NVLS...). For testing.
NCCL_PROTO=SimpleForces a protocol (LL, LL128, Simple). For testing.

Key takeaways

  1. AI training is a team sport. GPUs must share results after every step, so the network is part of the computer.
  2. Every extra copy and every trip through the CPU costs time. The best paths have no stops.
  3. Inside a server, NVLink and NVSwitch are the motorway. PCIe is the side road.
  4. Between servers, RDMA removes CPU copies, and GPUDirect RDMA removes system memory too.
  5. NCCL finds the roads, picks the plan and moves the data. You rarely call it directly.
  6. Learn the six collectives. AllReduce is the star, and it is just ReduceScatter + AllGather.
  7. Ring is best for big messages, tree for small ones at scale, and in-switch reduction beats both when you have it.
  8. Test with nccl-tests, read busbw, and check the log for GDRDMA.
