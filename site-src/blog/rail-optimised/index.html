Rail-optimised fabrics, explained

Why AI clusters wire their network "by rail", and how that one idea keeps GPU traffic just one switch hop away.

1. Start inside one GPU server

A modern AI server (an HGX or DGX box) has 8 GPUs. To keep the pictures simple, the diagrams here show 4 GPUs per server. The idea is exactly the same with 8.

Two things matter inside the server:

  • NVLink and NVSwitch join all the GPUs in the box. This is the very fast road inside the server.
  • One network card (NIC) per GPU. Each GPU shares a PCIe switch with its own NIC, so it can send straight out to the network with GPUDirect RDMA.

2. So what is a rail?

Number the NICs in every server the same way: NIC 0, NIC 1, NIC 2, NIC 3.

A rail is the group of all the NIC 0s from every server, connected to the same leaf switch. All the NIC 1s go to another leaf, and so on. So with 8 GPUs per server you get 8 rails and 8 rail leaf switches.

Think of it as

A school where every class has a pupil 1, pupil 2, pupil 3 and pupil 4. All the pupil 1s share one minibus, all the pupil 2s share another. Pupil 1 from any class can reach pupil 1 from any other class on the same bus, with no changes.

Why number them? Because of how AI training talks. NCCL builds its rings and trees so that GPU n on one server talks to GPU n on the other servers. If GPU n always uses NIC n, and all NIC n's sit on the same switch, that traffic needs only one switch hop.

3. Wiring the rails

Watch the cables go in. Each colour is one rail. Notice that every server sends one cable to every leaf, not all its cables to one leaf.

4. Rail vs top-of-rack: count the hops

The traditional data-centre design is top-of-rack (ToR): every cable from a server goes to the switch at the top of its own rack. That is great for normal apps. For AI it means GPU 0 in one rack must climb up to a spine and back down to reach GPU 0 in another rack.

5. A whole AllReduce on rails

Now scale it up. In a real training step, every GPU sends at the same time. NCCL runs one ring per rail, all in parallel. GPU 0s pass data around rail 0, GPU 1s around rail 1, and so on.

Watch the spine switches in each mode. With rails they stay quiet. With top-of-rack, they light up with traffic.

Less traffic on the spines means fewer shared queues, less congestion and less tail latency. In synchronous training, the slowest message decides the speed of every GPU, so tail latency matters a lot.

6. Crossing rails with PXN

Not all traffic is "GPU n to GPU n". AllToAll (used by Mixture-of-Experts models) and pipeline parallelism often need GPU 0 on one server to reach GPU 3 on another.

Without help, that message leaves on rail 0, climbs to a spine, and comes down on rail 3. NCCL has a trick called PXN (PCI × NVLink), added in NCCL 2.12. It first moves the data over the server's own NVLink to local GPU 3. Then GPU 3's NIC sends it on rail 3, one hop to the destination.

PXN does not go through the CPU. The path is GPU → NVLink → the other GPU → its PCIe switch → its NIC. NCCL can also bundle messages from several local GPUs heading to the same place. NVIDIA reported more than 2× faster AllToAll with PXN.

7. When a rail switch fails

Rails also limit damage. If one rail leaf fails, only that rail in that group of servers is hit. The other rails keep working, and NCCL can use NVLink to move the affected traffic over to a healthy rail.

The job keeps running, but rail 1 now carries two rails' worth of traffic, so that part of the job is slower. In practice you replace the switch quickly. Monitoring tools like UFM (InfiniBand) or NetQ (Spectrum-X Ethernet) show which rail is affected.

8. Scalable units: building in blocks

Real AI factories are built from repeatable blocks called scalable units (SUs). In NVIDIA's DGX SuperPOD designs for H100, H200 and B200, one SU is 32 servers. With 8 GPUs each, that is 256 GPUs, 8 rails and 8 rail leaves. Spine switches then join the SUs together.

Try the calculator. It sizes a simple two-tier, non-blocking fabric: every leaf has as many uplinks to the spines as it has links down to servers.

The default values match the worked example in my book: 2 SUs of 32 servers on 64-port switches need 16 rail leaves and 8 spines. Always check the current NVIDIA reference architecture for your exact platform, because SU sizes change between generations. For example, a DGX GB200 SU is 8 NVL72 racks.

9. How to check your rails are right

Rails only help if the cables and software match the plan. One crossed cable can push a whole job's traffic onto the spines. Here are four quick checks:

  1. GPU to NIC pairing. Run nvidia-smi topo -m. Each GPU should show PIX (same PCIe switch) to exactly one NIC.
  2. Cabling. Check that NIC n of every server lands on leaf n. Use LLDP or NetQ on Ethernet, or ibnetdiscover and UFM on InfiniBand, and compare against the cable plan.
  3. What NCCL chose. Run nccl-tests with NCCL_DEBUG=INFO and check that GPU n uses NIC n, and that you see GDRDMA.
  4. Spine counters. During a job that fits in one SU, spine links should be fairly quiet. Busy spines plus quiet rail leaves usually mean crossed cables.
# GPU-to-NIC affinity: look for PIX on the diagonal
nvidia-smi topo -m

# all-reduce across nodes, with NCCL's choices printed
NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=INIT,NET mpirun -np 64 -N 8 ./build/all_reduce_perf -b 1G -e 4G -f 2 -g 1

# InfiniBand: which switch is each HCA cabled to?
ibnetdiscover | grep -i mlx5

10. Cheat sheet

TermPlain English
RailAll NIC n's from every server, on the same leaf switch.
Rail leafThe leaf switch that serves one rail.
Top-of-rack (ToR)Old design: all of a server's cables go to its own rack's switch.
Scalable unit (SU)A repeatable block of servers plus their rail leaves. 32 servers in DGX SuperPOD (H100/H200/B200).
PXNNCCL trick: hop over NVLink to the GPU on the right rail, then go out its NIC.
Non-blockingA leaf has as much bandwidth up to the spines as down to the servers.
Rail-onlyA research idea with no spines between rails at all. All cross-rail traffic goes over NVLink. Not used in DGX SuperPOD.
NCCL_IB_HCATells NCCL which NICs it may use (for example only the 8 compute NICs).
NCCL_CROSS_NICWhether NCCL may use different NIC numbers on different servers in one ring. Leave it at the default on a rail fabric.
NCCL_PXN_DISABLETurns PXN off. Useful only for testing.

Key takeaways

  1. Give every GPU its own NIC on the same PCIe switch.
  2. Send NIC n of every server to leaf n. That group is a rail.
  3. NCCL pairs GPU n with GPU n, so collective traffic stays on one rail, one switch hop away.
  4. Spines then carry mostly traffic between rails and between scalable units.
  5. PXN uses NVLink to reach the right rail, so cross-rail messages also avoid the spines.
  6. A failed rail leaf hurts one rail, not the whole job.
  7. Build in scalable units and check the cabling, because one crossed cable undoes the benefit.
